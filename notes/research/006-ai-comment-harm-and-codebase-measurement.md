# AIが書くコメントは有害か（主張の検証とコードベースの実測）

### 背景・目的

「Agent のコメントを禁止するとバグが減る」という X の投稿（@cu30rry_・2026-09-04・♥487・views 73,856）をきっかけに、ハーネスの出力量が全面的に過剰ではないかという疑いを検証した。あわせて joifup のコードを実測し、過剰さが実在するか、実在するなら何が過剰なのかを特定した。**`tasks/006` の調査の一部であり、原則・思想そのものの調査は未着手である。**

**限界**: X の投稿は自己申告であり、後半は `pstack` というツールの宣伝を含む。学術側も参照した論文数は少なく、コメント比率の一般的な水準との比較は取っていない。確認日はすべて 2026-09-07〜08。

### 調査結果

#### 元投稿の主張

**概要**: ①「Agent のコメントを禁止するとバグが減る」は事実 ②コメントが多いファイルほど欠陥が多いのは観測されており LOC の代理指標だった ③Agent はコメントを「仕事を進めた」と認識するので、後から禁止ルールを書いても目標関数が勝つ ④必要なのは禁止文ではなく最初から書かせないハーネス。

- **支持できる部分**: コメントが次ターンのコンテキストを汚し、以後の判断の根拠になるという指摘。コストと陳腐化の観点では正しい
- **支持できない部分**: ①は下記の研究と矛盾する。②はコメント密度を LOC で統制した研究が見つからず、そもそも欠陥密度とサイズの関係自体が論争中（大きいモジュールほど欠陥密度が低いという結果もある）。③は出典のない推測
- 参考: https://x.com/cu30rry_/status/2095843317023961524 / https://arxiv.org/pdf/1511.03194

#### 研究: コメント削除の効果はタスクで反転する

**概要**: `Inside Out: Uncovering How Comment Internalization Steers LLMs for Better or Worse`（arXiv 2512.16790）は、Concept Activation Vector でコメント概念を内部的に無効化して効果を測った。Qwen2.5 系3種（Coder / 汎用 / 推論）、Java、3タスク。

| タスク | コメントを無効化すると |
| --- | --- |
| コード翻訳 | **最大 +67% 改善** |
| コード補完 | 最大 −22% 悪化 |
| **コード修正（refinement）** | **最大 −90% 悪化** |

- **含意**: エージェントが日常的に行うのは refinement であり、そこで削除が最も害になる。**「一律禁止でバグが減る」は支持されない**
- **より重要な知見**: Macke & Doyle は「**誤ったコメントは性能を大きく劣化させるが、欠落や不完全さの影響は小さい**」と報告している。問題はコメントの量ではなく、コメントが嘘になること
- 他の報告は方向が割れる: Liu et al.（RepoQA）は多くの LLM で削除が改善（Gemini は例外）、Imani et al. はコード要約で削除が改善、Nikiema et al. は有意差なし。また**誤ったコードほどコメントが多い**という相関も観測されている
- 参考: https://arxiv.org/html/2512.16790v1 / https://arxiv.org/html/2607.01867v1

#### Anthropic の方針（ルールの列挙から判断の委譲へ）

**概要**: Claude Code のシステムプロンプトの80%超を削除しても性能が落ちなかったとされ、Claude 5 世代向けに指示の作法が変わったと説明されている。旧「ルールを列挙する」→ 新「判断を任せる」。

> **「コメントを書くな」のような固定ルールは、状況によっては間違った指示になる。**新世代は「周囲のコードの密度や流儀に合わせろ」で正しく判断できる

- **メリット**: 上の研究（タスク依存で±が反転する）と整合する。元投稿の処方（禁止をハーネスで強制）はモデル世代の変化と逆を向いている可能性がある
- **デメリット / 前提**: 「**周囲の流儀に合わせろ」は、すでに健全なリポジトリを前提にした指示である。** 悪い慣習が染み付いている場合は固定化に働き、改善に向かわない（本件がまさにその状態）
- 参考: https://x.com/RadineerE10/status/… （2026-07-27・要一次情報の確認）

#### 実務側の知見

- **検証はリンターに寄せる**（@harumak_11・♥815）— 「コードレビューでトークンを燃やすのはもうやめよう。結局カスタムリンターが最適だとわかった」。検証プロセスがボトルネックになるため、検証速度を超えてリリースはできない
- **認知的降伏（cognitive surrender）**（同・♥133）— オフローディングは手順を任せて判断は自分が下す状態、降伏は自分で答えを組み立てず AI の出力をそのまま自分のものにしてしまう状態。**AI が使える環境では誤った答えでもそのまま受け入れる人が多い**。本人が自己申告している「仕様書・PR を流し見で承認してしまう」はこの既知の現象に当たる
- **「全部入れない」**（@SuguruKun_ai）— AI が判断基準として使える情報だけを残す
- Ponytail（@djrio_vr・♥2890）は「過剰な設計・存在する部品の再発明・冗長なコメント」を無言で削る方向のスキル。`006-harness-token-efficiency` で既に実測済み

#### joifup の実測（2026-09-08）

`node_modules` / `target` / `dist` / `.claude` を除外、445ファイル。

| | コード | コメント | 比率 |
| --- | --- | --- | --- |
| Rust | 24,916 | 10,727 | **43.1%** |
| TypeScript | 46,643 | 14,812 | 31.8% |
| TSX | 29,108 | 9,995 | 34.3% |
| **合計** | **100,667** | **35,534** | **35.3%** |

上位ファイルはコメントがコードの **2.6〜3.7倍**（`apps/web/src/lib/events.ts` 372% / `joifup-node-stop-event.ts` 303% / `use-pin-status.ts` 266%）。

**`events.ts`（定数を3つ export するだけ、コメント160行 / コード43行）の中身を分類した結果**:

| 種類 | 本来の置き場所 |
| --- | --- |
| 本物の why（同一タブでは focus が発火しない、等） | **コメントで正しい** |
| 履歴・考古学（「元々は今は無い◯◯ボタン用に書かれた」） | git |
| タスクIDの鎖（task-136 / 127 / 157 / 178 / 175） | git・notes |
| 他ファイルの動作の再説明（「AppSidebar は◯◯でしか refetch しない」） | そのファイル |
| 設計判断の根拠（「配列 → 型の向きで derive する」） | **設計書** |

**最後のカテゴリは実際に二重化していることを確認した。** `notes/document/178-sidebar-event-source-id-design.md` に同じ根拠が書かれている（sourceId / origin の言及23箇所）。

### 比較表

| 主張 | 証拠の強さ | 判定 |
| --- | --- | --- |
| 誤ったコメントは性能を損なう | 実験あり | **支持** |
| コメントは次ターンのコンテキストを汚す | 自明（コスト面） | **支持** |
| コメント削除は一律で有効 | 実験が反証（refinement で −90%） | **否定** |
| コメントが多い＝欠陥が多い（LOC 代理） | 該当研究が見つからず、前提の相関も論争中 | **未検証** |
| Agent がコメントを「進捗」と認識する | 出典なし | **推測** |
| 固定ルールより判断の委譲がよい | ベンダーの説明＋研究と整合 | **支持（ただし健全なリポジトリが前提）** |

### 結論・推奨

1. **過剰なのは「コメント」ではなく「複製」である。** joifup は設計書に why を書いたうえで、同じ内容をコードコメントに写している。さらに git が持つ履歴と notes が持つタスクの鎖も写されている。だから量が3倍になる。
2. **写しは必ず陳腐化し、陳腐化したコメントこそが実際に性能を落とす**（Macke & Doyle）。ここで因果が閉じる。量が問題なのではなく、**一次情報が二重にあることが問題**である。
3. **したがって新しい規則は要らない。** 「記録（log・背景情報）はマキシマム、成果物はミニマム」という既存の原則を、コードにも適用すればよい。根拠は notes に置き、コードには**そこへのポインタと、コードから復元できない why だけ**を残す。→ `tasks/007`
4. **「コードから復元できない why だけ」をリンターで機械判定するのは不可能である。** 判定できるのはコメント比率、TODO の残存、コメントとコードの語彙一致（＝言い換えの検出）程度で、本質的な why かどうかは意味の判断になる。規則を増やす方向では解けない。
5. **「周囲の流儀に合わせろ」はこのリポジトリにそのまま適用してはいけない。** 現状の慣習が過剰なので、流儀ではなく原則に合わせる形にする必要がある。

### 残課題

- **本題（`tasks/006` の主目的）が未着手である。** 「log はマキシマム / 成果物はミニマム」という分け方の妥当性、うまく回っているハーネスがどういう原則で成り立っているか、ルールの列挙と原則の少数配置のどちらがどの場面で効くか——これらは本調査では扱っていない
- Anthropic のシステムプロンプト80%削除の件は X 経由の二次情報であり、**一次情報に当たっていない**
- コメント比率 35.3% が一般的な水準に対して高いのかを比較していない。**内部の二重化という証拠のほうが強いので判断には影響しないが、数字を対外的に出すなら要確認**
- 実測は joifup のみ。fde の `tools/` 配下と dotfiles のスキル群は測っていない
- 人間が読む面（spec・plan・PR本文・セッション出力）の過剰さは測定していない。コードとは別の軸で、こちらは**流し見と追認**という具体的な害が既に出ている
