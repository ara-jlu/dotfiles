# j-devflow の設計書に fresh なレビューを入れる

## 背景と問題

`j-devflow` の Phase A では、設計書（spec）は書いた本人の自己レビューしか通らない。書いた本人は設計の対話で前提を共有しているので、その前提自体の抜けは自己レビューでは見えない。

2026-10-02、fde の `tasks/097` で、自己レビューを通した設計書に、題材の芯に関わる穴（受け取り方の前提から、添付で届く注文書を扱えなくなる）が残り、依頼者が読んで見つけた。設計書の穴は Phase B のどのレビューも計画と設計書を基準にするので捕まらず、手戻りが最も大きい。

## 上流の計測との関係

superpowers は v5.0.6（2026-03-24）で、設計書と計画を fresh な subagent にレビューさせるループを廃止し、書いた本人の自己レビューのチェックリストに置き換えた。RELEASE-NOTES の記述は「実行時間が倍（約25分）になり、計画の品質は計測上上がらなかった。5版×5試行で品質スコアが同一」「自己レビューは約30秒で1回あたり3〜5件の実際の bug を捕まえ、欠陥率は subagent の方式と同程度」である。

この計測は 016 の決定を否定しない、と判断した理由:

- **測った指標は計画の品質である。** 設計書のレビューの効果も、計画の品質を通して間接に測られている。
- **廃止された spec レビュアーの観点（完全性・一貫性・明確さ・スコープ・YAGNI）は、置き換えた自己レビューのチェックリスト（placeholder・internal consistency・scope・ambiguity）とほぼ同じである。** 同じ観点を別の目で見ても差が出にくいのは自然である。
- **016 が狙うのは、題材の実態に照らした前提の抜けである。** 上流の比較のどちら側にも、この観点は無い。

手元の証拠は小さい（097 の事故1件と、016 の設計書自体での試行1回で、自己レビューの後に Important が計8件出た）。よって directional として扱い、下の「検証」をこの決定の要とする。検証で新しいプロンプトの優位が出なければ、決定を見直す。

## 決定事項

### 1. 設計書の fresh レビュー（手順 3、GATE 1 の前）

**位置:** brainstorming の checklist 7（設計書の自己レビュー）の後、checklist 8（書いた設計書を人間が読む）の前。brainstorming では節ごとの設計の承認（checklist 5）は設計書を書く前に済むので、書いた設計書を読ませられるのはこの間しかない。j-devflow の GATE 1 は checklist 8 の「書いた設計書の承認」を指すと SKILL.md に明記する。j-devflow は既に手順 3 で設計書の置き場所（staging）を brainstorming に指定しており、checklist の間に dispatch を挟むのも同じ「順序の指定」である。brainstorming の checklist 8 自体が「After the spec review loop passes」と書いており、レビューを挟む足場がある。

**渡すもの:** タスク本文のパスと、staging の設計書のパスだけ。会話は渡さない。設計書が参照する既存のファイルは読んでよい。Worktree 固定の契約（`Worktree root: <WT>`、最初の行動として `cd "<WT>"` と toplevel の一致の assert、不一致なら BLOCKED）に従わせる。レビュアーは何も書き換えない。

**Worktree 固定の契約 (c) の例外:** 設計書のレビュアーには、staging の設計書（scratchpad）・タスク本文・設計書が参照する `<WT>` の外のファイルを、**読み取り専用の入力として絶対パスで**渡してよい。契約 (c) の目的は主チェックアウトへの書き込みの漏洩を防ぐことで、何も書き換えないレビュアーの読み取りはその対象でない。staging を `<WT>` の中に置くと untracked のまま commit に混ざる危険があるので、置き場所は scratchpad のままにする。

**観点:** j-devflow が持つ専用のプロンプト `.claude/skills/j-devflow/references/spec-review-prompt.md`（新規。日本語）に書く。観点は次の4つで、①②が主である。

1. **目的への適合** — タスク本文が果たしたいことを、この設計で果たせるか。タスク本文は概要レベルで設計の権威ではないが、目的の物差しには使う。
2. **前提の抜け** — 題材の実態（入力の届き方と形式・使う人・例外・規模）に照らして、扱えない物が残っていないか。設計書が暗に置いている前提を書き出させ、それぞれが実態と合うかを問わせる。
3. **自己完結** — TBD・内部の矛盾・二通りに読める要件・定義されていない語・既存のファイルの記述との食い違い。
4. **スコープ** — 1つの計画に収まるか。

**出力:** 2つを返す。

- **指摘:** 指摘ごとに重さ（Critical / Important / Minor）・設計書の該当箇所・根拠・なぜ問題か。指摘が無ければ無いと返す。
- **前提の一覧:** 設計書が暗に置いている前提を書き出し、それぞれ「合う / 合わない / 不明」と、**合わなかったら目的を果たせなくなるか（芯）**の印を付ける。fresh なレビュアーが題材の実態を知る手段はタスク本文とファイルだけなので、実態が依頼者の頭の中にしか無い前提は「不明」になる。097 の穴はこの型（依頼者が読んで見つけた）なので、「不明」を無理に指摘に変換させず、一覧のまま人間に見せるのが捕まえる経路である。

**指摘の扱い:** 書いたセッションが指摘を1件ずつ「直した / 判断を仰ぐ / 採らない（理由）」に振り分ける。Critical / Important、または前提の一覧で「合わない」かつ芯の前提を直したら fresh に再レビューする（修正したセッションの自己チェックにしない。芯の前提を書いた本人が直しただけで自動承認に進めない）。再レビューには、会話は渡さず、**前回の指摘と振り分けの表を渡し**、各指摘が解消したか・「採らない」の理由が成り立つかの判定と、新しい指摘を求める（渡さないと「採らない」とした指摘が毎回出直して上限を空費する）。再レビューは2回までとし、それでも Critical / Important が残れば下のモード別の扱いに回す。Minor はブロックしない。直した物が無く「採らない」「判断を仰ぐ」だけのときは再レビューを回さない。その理由の妥当性は、attended では GATE 1 で人間が判断し、`-auto` では下のとおりエスカレーションするので、どちらでも第三者が見る。

- **attended:** GATE 1 で、設計書に振り分けの表と、前提の一覧のうち「合わない」「不明」を添えて人間に出す。指摘や前提で推奨アプローチが崩れたときは、人間の判断で checklist 5（節ごとの提示）に戻る。
- **`-auto`:** 次のいずれかが残れば自動承認せず、`-auto` のエスカレーション条件として dispatcher に問う。
  - 「直した」以外に振り分けた Critical / Important（「採らない」「判断を仰ぐ」を含む。書いた本人が退けた指摘で自動承認しない）
  - 指摘を直した結果として推奨アプローチが変わった（直して再レビューが clean でも止める。推奨アプローチを決め直すのは人間である。前提を直しただけで推奨アプローチが変わらなければ、fresh な再レビューが clean なら自動承認してよい）
  - 再レビュー2回で解消しきれない指摘
  - 前提の一覧で「合わない」かつ芯の印が付いた前提

  どれも残らなければ自動承認する。**「不明」かつ芯の前提ではエスカレーションしない。** 設計書に「未確認の前提」の節を設けて書き残し、手順 10 で **PR 本文の冒頭に転記する**（設計書のファイルが diff に入るだけでは人間の目に届かない）。j-devflow は手順 10 で既に PR 本文に載せる節を指定しているので、その指定に足す。attended では GATE 1 で人間が一覧を見ているので、この節は作らない。fresh なレビュアーには実態の手段が乏しく、芯の前提は構造的に「不明」になりやすいので、これを止める条件にすると `-auto` がほぼ毎回止まる。`-auto` が受け入れているリスクは手戻り（PR で設計が却下される）だけなので、「不明」を PR まで運ぶのはその範囲に収まる。

**GATE 1 で人間が修正を求めたとき:** 修正後の設計書で fresh レビューをもう一度回す（再レビューの回数は数え直す）。人間が不要と言えば省く。

### 2. SKILL.md の他の箇所

- **`-auto` のエスカレーション条件:** 決定事項 1 の `-auto` の扱いで dispatcher に問う場合を、既存の箇条に足す。
- **手順 10:** `-auto` で設計書に「未確認の前提」の節があれば、PR 本文の冒頭に転記する。
- **手順 3 の「subagent には絶対にしない（これは設計の対話である）」:** 対象が設計の対話そのものであることを明確にし、書いた設計書の読み取りレビューは subagent に出すと書き分ける。
- **Worktree 固定の契約 (c):** 決定事項 1 の例外を足す。
- **ガード:** 「設計ゲート」に、GATE 1 の前に設計書の fresh レビューを通すことを足す。
- **よくある失敗:** 「設計書を、書いた本人の自己レビューだけで通す」を足す。
- **why の置き場所:** 097 の実例、上流の計測との関係、同梱の `spec-document-reviewer-prompt.md` を使わない理由はこの設計書に置く。SKILL.md と専用プロンプトには、この設計書へのポインタと、文面から復元できない最小の理由だけを書く（`.claude/rules/comment-rationale.md`）。SKILL.md は symlink で全リポジトリから読まれるので、ポインタは「dotfiles の `notes/document/…`」とリポジトリ名付きで書く（`CLAUDE.md` が 008 を指す書き方と同じ）。
- **適用範囲:** fresh レビューは Phase A に入るので、`-light -auto` を含む全モードに効く。Phase B の手順と `-light` の定義には触れない。
- **`tasks/017` への申し送り:** 017 の背景は 016 を「設計書と計画に fresh なレビューを入れる」と書いているので、「設計書に」へ直す（計画のレビューは外した）。
- **コスト:** 1回の設計書につき dispatch が最小1回、再レビューを含めて通常3回まで増える（GATE 1 で人間が修正を求めれば数え直す）。上流の計測では subagent のレビューのループ1つで約25分かかった。`-light -auto` の動機（プロセスのオーバーヘッドを減らす）とは逆向きのコストだが、設計書の穴は Phase B のどのレビューでも捕まらず手戻りが最も大きいので、モードで外さない。既定を light にする `tasks/017` は、この前段の厚みを前提の1つとして検討する。

## 採らなかった案

- **計画にも fresh レビューを入れる（同梱の `plan-document-reviewer-prompt.md` を無改変で使う）。** 一度は採ったが外した（依頼者の判断。2026-10-02）。上流が計測のうえ廃止した部品そのものであり、置き換えた自己レビューのチェックリストに spec coverage（設計書の要件が計画に入っているかの突き合わせ）が入っている。無改変の雛形は重さの無い Approved / Issues Found しか返さず、指摘の振り分けと噛み合わない。計画で設計書の要件が落ちる事故が実際に起きたら、改めて起票する。
- **同梱の `spec-document-reviewer-prompt.md` を使い、観点を dispatch 時に書き足す。** 観点がすべて文書の中で閉じた検査で、「Approve unless there are serious gaps」という承認寄りの較正なので、書き足す前提の検査とぶつかる。上流が効果なしと測ったのもこの観点である。
- **`CLAUDE.md`「レビュー統合」に一般規則として書く。** j-devflow の外の設計書にも効くが、毎回読む面が太り、dispatch の具体（何を渡すか・いつ・指摘の扱い）を書けない。
- **GATE 1 の後、md2joifup の前に置く。** 人間の目と独立に見られるが、指摘で直すと再承認が要る。GATE 1 の前に置けば、人間は指摘込みで1回読めば済む。
- **観点を「目的への適合」だけに絞る。** 依頼者の判断で、自己完結の検査も併せて持たせる（2026-10-02）。

## 検証

`tasks/097` の確定した設計書から、添付で届く注文書の扱いを抜いて穴を再現した版を作る。fde の `tasks/097` の本文と合わせて、次の2つに fresh に読ませる。それぞれ2回ずつ試す（LLM の出力は揺れる）。

- 同梱の `spec-document-reviewer-prompt.md`（比較の基準）
- 新しい `spec-review-prompt.md`

**入力を揃える:** 両者に同じ物を渡す。同梱の雛形には `[SPEC_FILE_PATH]` の枠しか無いので、タスク本文のパスは雛形の外の前置きで渡す（新しいプロンプトの dispatch と同じ前置き）。

**合格:** 新しいプロンプトが2回とも、**添付のファイル（注文書・図面の PDF や Excel など）で届く入力を扱えるか**を名指しして、次のいずれかで挙げる。

- Critical か Important の指摘
- 前提の一覧で「合わない」、または「不明」かつ芯の印（決定事項 1 の言う捕まえ方）

「入力の届き方: 不明」のように添付を名指ししない一般的な挙げ方は合格に数えない。097 のタスク本文は入口に「Excel」を挙げるが、添付のファイルで届くこと自体は書いておらず、それはレビュアーが題材の実態から推して挙げる必要がある。それができることが、この観点の効きそのものである。

**同梱のプロンプトが「捕まえた」の判定:** Issues（Recommendations ではない）に、同じく添付の入力の扱いを名指しした指摘があること。

**不合格のときの扱い:**

- **新しいプロンプトが見逃す:** プロンプトを直して再試験する。
- **同梱のプロンプトも2回とも捕まえる:** 「上流の計測との関係」の区別が崩れたことになる。プロンプトを直すのではなく、決定（専用のプロンプトを持つ）そのものを依頼者と見直す。

確定版の設計書は fde のセッションの作業領域にあり、2026-10-02 時点で存在を確かめた。消えていたら、fde の 097 のブランチに永続化された設計書から作る。dotfiles は public で fde は private なので、再現版の設計書・fde の本文・その所在はリポジトリに入れず、PR にも結果だけを一般化して載せる。検証は計画の1タスクとして行い、成果物を commit しない。

## 検証の結果

2026-10-08 に行った。どの試行も、fresh な subagent が穴を再現した設計書とタスク本文を読んだ。

- **1回目（タスク本文そのまま）:** 同梱のプロンプトも新しいプロンプトも、2回とも穴を挙げた。ただし同梱の側の経路は、タスク本文が入口に挙げる「Excel」が設計書に無いという、書かれたこと同士の食い違いだった。新しい側は、設計書が参照する題材の調査記録を読んで実態を確かめ、Critical で挙げた。決定の見直しの分岐に当たったので、依頼者の判断で、ヒントを消して再試験した。
- **再試験（タスク本文の写しから「Excel」を消した）:** 同梱のプロンプトは2回とも Approved で、穴を挙げなかった。新しいプロンプトは2回とも、添付で届く図面と注文書を扱えないことを Critical で挙げ、前提の一覧でも「合わない」かつ芯とした。
- **付随して:** 新しいプロンプトは4回とも、同梱の側が一度も挙げなかった前提の穴を、ほかにも挙げた。

097 の事故の時点のタスク本文にも「Excel」は書かれていたので、097 の穴は、書いた本人でなければタスク本文との食い違いとしても見えた。ただし同梱の雛形にはタスク本文を渡す枠が無い。再試験では前置きでタスク本文を渡しても、本文に字面のヒントが無いと見逃した。再試験は 1 回目の結果を見てから入力を変えたものなので、証拠は directional として扱う。よって専用のプロンプトを維持する（依頼者の判断。2026-10-08）。
