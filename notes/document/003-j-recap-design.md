# j-recap — 作業成果の外部向けまとめスキル 設計

- **日付:** 2026-07-26
- **スキル名:** `j-recap`
- **配置:** `~/Joifup/dotfiles/.claude/skills/j-recap/SKILL.md`
- **種別:** user-invocable スキル（`/j-recap`）

## 目的

指定期間（デフォルト=今日）に進めた／完了したタスクを、episodic-memory の会話記録から拾い、**タスク単位で「進捗ステータス＋概要」**にまとめ、**外部公開できる文章**（X 投稿レベル）にしてチャットに出力する。

内部再現用のログ（既存 `j-log`）でも、Joifup ノートへの永続化（`j-doc` / `j-research`）でもない。**読み手が社外／第三者**である点が本質的な差。

## 背景・動機

このスキルは実体験から生まれた。ある日の成果を episodic-memory 検索だけで要約したところ、実際には PR マージ・実装完了まで進んでいた作業が「設計まで」に見えてしまった。**会話記録は"何を話したか"の記録であって、"何が実際に完了したか"の真実ではない。** そのため本スキルは記録の要約で終わらせず、git / PR の実体で裏取りする2段構えを核心に据える。

## スコープ / 非スコープ

- **スコープ:** 記録の横断検索 → 実体の裏取り → サニタイズ → 2形式のテキスト出力（チャットのみ）。
- **非スコープ（YAGNI）:**
  - X への自動投稿・API 連携はしない（人間が貼る前提）。
  - Joifup ノートやファイルへの永続化はしない（チャット出力のみ）。
  - 画像・OGP 生成はしない。

## 入力（引数）

`$ARGUMENTS` で対象を上書きできる。省略時は**今日**。

- 省略 → 今日（`currentDate` を使用。`Date.now()` 等は使わない）
- `2026-07-20` のような日付 → その日
- `this-week` / `last-week` / `2026-07-20..2026-07-26` のような期間 → その範囲
- プロジェクト名（例 `joifup`）→ 対象プロジェクトで絞り込み（省略時は横断＝その日に触れた全プロジェクト）
- 日付と絞り込みは併用可（例 `/j-recap this-week joifup`）

## フロー（2段構え）

### 1. 拾う — episodic breadth search

`episodic-memory:search-conversations` サブエージェントを使い、対象期間のセッションを**複数クエリ・日付フィルタで横断的に**洗い出す。

- サブエージェントへの依頼内容: 対象期間の全セッションを、タスク／リポジトリ／成果物（コミット・PR・作成ファイル）単位で構造化して報告させる。憶測を禁じ、記録ベースの事実のみ。
- 出力として「タスク候補リスト」を得る（各候補にプロジェクト／リポジトリ、関与ファイル、記録上のステータス）。

### 2. 裏取り — git / PR truth

拾った各タスクについて、対象リポジトリで**実体を確認**し、ステータスを確定する。

- 対象リポジトリで当日（対象期間）分・**全ブランチ**の `git log --all --since/--until` を確認。
- PR / マージの有無（マージコミット、`gh pr` 等が使えれば併用）で完了度を判定。
- ここで得たコミットハッシュ・PR 番号は**完了判定の根拠としてのみ使い、最終出力には出さない。**

### 3. サニタイズ（外部公開前提）

- 内部識別子（`TASK-<n>`、内部リポジトリ名、未公開の固有名詞、社内ツール名）を一般化・伏字にする。
  - 例: 「TASK-88 richEditor round-trip audit」→「リッチエディタの Markdown 往復変換の忠実性改善」
- 機微情報（認証情報、顧客名、未公開のプロダクト名）は出さない。判断に迷うものは丸めるか省く。

### 4. 出力（2種を併記、チャットのみ）

**A. 短文ポスト版** — 各タスク 1〜数本、X にそのまま貼れる短さ。絵文字／ハッシュタグは控えめ。1本 ≈ 140 字前後を目安。

**B. まとめ段落版** — その日の成果を数段落の読み物に。ブログ／日報寄り。

いずれも各タスクは「**何を進めたか / 完了したか（ステータス）＋ 概要**」の形。コミットハッシュの羅列は禁止。

## ステータス判定ルール

実体（裏取り）に基づき、各タスクを次のいずれかに分類する：

| ステータス | 判定根拠の例 |
|---|---|
| **完了** | PR マージ済み、UAT 承認済み、対象ブランチが main に到達 |
| **進行中** | worktree／feature ブランチにコミットはあるが未マージ、設計・実装途中 |
| **設計・計画** | ドキュメント／spec のみ作成、実装未着手 |

記録と実体が食い違う場合は**実体を優先**し、その旨（記録上は設計まで見えたが実際はマージ済み等）は内部判断に留め、出力は確定ステータスで書く。

## 出力フォーマット（例）

```
## 📊 作業まとめ（2026-07-21）

### 短文ポスト版
1.（完了）リッチエディタの Markdown 往復変換で崩れていた記法を洗い出し、
   忠実性を改善する修正をリリースまで完了。48ケースの回帰テスト付き。
2.（進行中）ファイル監視まわりで双方向リンクを自動同期する仕組みを設計中。

### まとめ段落版
今日は主にエディタの信頼性向上に取り組んだ。Markdown と……（数段落）
```

## 依存

- `episodic-memory:search-conversations` サブエージェント（記録検索）
- `git`（裏取り）、あれば `gh`（PR 状態）
- `currentDate` コンテキスト（日付の基準。時刻取得 API は使わない）

## 命名の根拠

既存の運用スキル群 `j-*`（`j-log` / `j-doc` / `j-task` …）に一貫。`recap`（振り返り・要約）は用途を description と argument-hint で補う。

## 想定される失敗・注意

- 記録のみで完了判定しない（本スキルの存在理由）。
- 横断検索で対象外プロジェクトの雑音を拾ったら、裏取り段階で当日コミットが無いものは落とす。
- サニタイズ漏れは外部公開事故に直結するため、固有名詞は保守的に丸める。
