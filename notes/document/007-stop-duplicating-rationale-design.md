# 一次情報の二重化をやめる

## 目的

設計判断の根拠が、notes の設計書とコードコメントの両方に書かれている状態をやめる。根拠は notes 側に1箇所だけ置き、コードにはそこへのポインタと、コードから復元できない why だけを残す。

**新しい規則は足さない。** `tasks/006` の調査が出した結論は「量が問題なのではなく、一次情報が二重にあることが問題である」であり、必要なのは既存の原則（記録は Joifup、成果物は最小）をコードにも適用することである。

## 二重化の実証（dotfiles 内）

`unwrap.py` は冒頭の docstring で正典の所在を宣言している。

> **規約と変換規則の正典は notes/document/008-no-hard-wrap-japanese-design.md**（dotfiles）である。検証の4条件は、すべてそこで決めている。

そのうえで、同じ根拠を本文に写している。

| `unwrap.py` | `notes/document/008-no-hard-wrap-japanese-design.md` の対応箇所 |
| --- | --- |
| `:444` 検証5条件の列挙 | `## 検証` の 1〜5 |
| `:452` 「5つ目が残りを塞ぐ」＋自己参照の説明 | `### 5つ目: 独立したパーサによる AST 比較` 第1段落 |
| `:394` 「1文字でも違えば欠陥」 | `### 5つ目` の正規化の項 |
| `:48` タブ展開が要る根拠 | `## 変換の規則` |
| `:215` `joins` を人間に見せる理由 | `### 検証を通ったあとに人間へ見せるもの` |

**そして既に陳腐化している。** 宣言文は「検証の**4**条件」のままで、設計書は5条件である。写しは必ず陳腐化するという指摘が、宣言した本人のファイルの中で、1ヶ月以内に発火していた。

これは「誤ったコメントは性能を大きく劣化させるが、欠落や不完全さの影響は小さい」（Macke & Doyle）が当たる形そのものである。ここで因果が閉じる。**量を減らすことが目的ではなく、嘘になる面を1つに減らすことが目的である。**

## 指針をどこに置くか

2層に分ける。**原則は常時、判定の表はコードを触ったときだけ。**

### 層1: `CLAUDE.md` § 記録先（常時ロード）

原則を2〜3行だけ足す。全セッションが毎ターン読む面なので長く書かない。判定の細目はここに書かない。

### 層2: `.claude/rules/comment-rationale.md`（新規・`paths` スコープ）

Claude Code の rules 機能を使う。公式ドキュメント（`code.claude.com/docs/en/memory`）で確定している事実:

- **`~/.claude/rules/` はユーザースコープの正式な置き場所である** —— 「Personal rules in `~/.claude/rules/` apply to every project on your machine」。マシン上のすべてのプロジェクトに効く。
- **`paths:` frontmatter でスコープできる** —— 「Path-scoped rules trigger when Claude reads files matching the pattern, not on every tool use」。マッチするファイルを読んだときだけ載るので、非コードのセッションではコンテキストを消費しない。
- ユーザースコープの rules はプロジェクトの rules より先に読まれ、プロジェクト側が優先される。

**`~/.claude/rules/` を選ぶ理由**は、joifup / fde に届くことである。プロジェクトスコープ（`.claude/rules/`）に置くと dotfiles の中でしか効かない。シンボリックリンクでプロジェクトに貼る道もあるが、ドキュメントによれば working directory の外を指すシンボリックリンクは外部 import 扱いになり、承認するまで読まれず、承認後も `paths` 付きのものは読まれない。**`paths` を使う以上、ユーザースコープ以外に選択肢は無い。**

### 既存の `.claude/rules/skill-language.md` は今は効いていない

`setup.sh` は `commands` / `docs` / `settings.json` / `skills` / `CLAUDE.md` をリンクするが、**`rules` をリンクしていない。** したがって `.claude/rules/skill-language.md` は dotfiles を作業ディレクトリにしたときしか載らず、`tasks/009` が意図した効力を持っていない。本タスクでリンクを足すことで、`skill-language.md` も同時に有効になる。

**制約として記録しておく**: Cowork のデスクトップセッションでは、working directory の外を指すシンボリックリンクの `~/.claude/rules/` は読み飛ばされる。ただし `~/.claude/CLAUDE.md` も同じ扱いを受けるとドキュメントに明記されており、この dotfiles の構成は既にその前提で動いている。新しく増えるリスクは無い。

## 判定の表

`tasks/006` の調査が `events.ts` の実物を分類して出した5種類を、そのまま判定の表にする。**推測ではなく実物の分類である。**

| 書こうとしている内容 | 置き場所 |
| --- | --- |
| コードから復元できない why（同一タブでは `focus` が発火しない、等） | **コメント。ここが唯一の一次情報** |
| いつ・誰が・なぜ変えたか（「元々は今は無い◯◯ボタン用に書かれた」） | git |
| タスクIDの鎖（`task-136` → `157` → `178`） | git・notes |
| 他ファイルの動作の再説明（「`AppSidebar` は◯◯でしか refetch しない」） | そのファイル |
| 設計判断の根拠（条件の列挙・トレードオフ・却下した案） | 設計書。コードには**1行のポインタだけ** |

### ポインタの書き方

**正典の場所を1行で指すだけにする。そこにある内容を要約しない。** 要約した瞬間に二重化が始まり、その要約が最初に陳腐化する。`unwrap.py` の「検証の4条件」がまさにそれで、指し先を書いた同じ文の中で数を写したために嘘になった。**数・条件の列挙・項目名は写さない。**

### 既存コードを触るとき

- **触った関数のコメントだけを見る。** ファイル全体の掃除はしない。
- **消す前に、その内容が設計書に本当にあるかを確かめる。** 無いなら消さずに設計書へ移す。コメントにしか無い why を消すことが、この作業で唯一の回復困難な損害である。

### 禁止形では書かない

「コメントを書くな」「設計書の内容をコピペするな」という固定ルールにはしない。`tasks/006` の調査で、コメントを内部的に無効化する実験がタスクによって符号を反転させることが分かっている（コード翻訳 +67%、補完 −22%、**refinement −90%**）。エージェントが日常的に行うのは refinement であり、そこで削除が最も害になる。**一律禁止は支持されない。** 判断を委譲する形で書く。

同じ理由で、リンターによる機械判定も作らない。`tasks/006` の結論4が確定させているとおり、「コードから復元できない why か」は意味の判断であり機械化できない。

## dotfiles の掃除

指針を自分のコードで先に検証する。対象は `.py` 8ファイル。

### 二重化の除去（非テストの5ファイル・547行）

`unwrap.py` / `uat_attach.py` / `measure_wraps.py` / `j_finish.py` / `md2joifup.py`。判定の表に従って分類し、設計書にある根拠はポインタ1行に畳む。

**テスト3ファイル（292行）は対象外。** テストのコメントは「何を固定しているか」の説明であり、設計書の写しではない。種類が違う。

### 記述言語の統一（`tasks/009` からの申し送り）

`md2joifup.py` が英語、`j_finish.py` / `uat_attach.py` がモジュール docstring だけ英語で以降は日本語。テスト3ファイルは既に日本語。**日本語に統一する。**

`CLAUDE.md` § 言語 の「機械が扱う面 = 英語、人が読む面 = 日本語」に従う。コメントと docstring は人が読む面である。英語のまま残すのは、既存の規定と同じく識別子・コマンド・パス・フラグ・型名・エラー文字列・原語で定着した技術識別子。

**新しいルールファイルは作らない。** 既存の `.claude/rules/skill-language.md` の `paths` を `.py` まで広げ、対象の記述を「SKILL.md」から「SKILL.md と自作スクリプト」に改める。`CLAUDE.md` § 言語 の該当行も同じく広げる。

### 折り返しの規約

新しく書くコメントは `notes/document/008-no-hard-wrap-japanese-design.md` の規約に従う（桁数で折り返さない）。既存の日本語コメントは既にこの形になっている。

## 適用の範囲と順序

**本タスクは dotfiles のみ。** joifup（38,178行）と fde（2,008行）は別タスクとする。1つの spec で 41,000 行を読み直すことはできないし、レビューも通らない。

**後続タスクの起票は本タスクでは行わない。** worktree で隔離されたセッションから他リポジトリへ書かないためである。マージ後に通常のセッションで、それぞれのリポジトリの `tasks/` に起票する。

後続タスクに申し送る内容:

- **指針は `~/.claude/rules/comment-rationale.md` にある。** 各リポジトリで内容を写さない —— それ自体が二重化である。
- **joifup のコメントは英語で統一されている。触らない。** 日本語化の規約は dotfiles の自作スクリプトに限定されており、joifup / fde には及ばない。
- **上位ファイルから当てる。** joifup は `apps/web/src/lib/events.ts`（372%）・`rich-editor/joifup-node-stop-event.ts`（303%）・`use-pin-status.ts`（266%）で、二重化の証拠（`notes/document/178-sidebar-event-source-id-design.md` との重複）が既に取れている。
- **全件をやらない。** 触るときに直す形に落とす。

## 検証

機械で判定できる部分が無いので、レビューで見る。

- **消したコメントの内容が設計書に存在すること。** 消した各箇所について、対応する設計書の節を示せること。示せないものは消さずに移す。
- **残したポインタが内容を要約していないこと。** 数・条件の列挙・項目名を含まないこと。
- **`unwrap.py` の「検証の4条件」が直っていること。** この欠陥は本タスクの出発点なので、残っていれば失敗である。
- **テストが green であること。** `python3 -m unittest test_unwrap -v`（139件）、`test_j_finish.py`、`test_uat_attach.py`。コメントの変更がコードの挙動を変えていないことの担保になる。
- **`setup.sh` の `rules` リンクが効くこと。** 実行後に `~/.claude/rules/` が dotfiles を指し、`comment-rationale.md` と `skill-language.md` の両方が見えること。

UI を変えないので UAT は行わない。
