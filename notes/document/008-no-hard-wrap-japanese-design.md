# 日本語のハード折り返しをやめる（設計）

## 目的

日本語の md 本文とコメントが桁数で折り返されている。日本語は語の間に空白が無いため、折り返しは語や句の途中で割れる。エディタが soft-wrap するので二重に折れ、意味と無関係な位置で2回切れる。折り返さないことを規約として置き、既存分は機械的に結合する。

## 実測

`~/Joifup` 配下の全リポジトリを測った。「折り返された行」の定義は「次の行が同じ段落の続きである行」（空行でも、見出し・リスト・表・フェンスの開始でもない行が次に来る）。frontmatter とコードフェンスの中は数えていない。

対象は 12 のリポジトリ、md 1,456 ファイル。折り返し率は repo によって 0% から 50% まで開いた。**日本語の折り返し行は合計およそ 21,940 行で、その 98% が 2 つの repo に集中している。** 残りの 10 repo は合わせて 400 行あまりで、うち 3 つは 1% 以下だった。

**0% の repo が実在することが、折り返しが必然ではないことを示している。** 3,036 段落行あって折り返しが 10 行しかない repo があった。また、英語本文が多い repo では折り返し 714 行に対し日本語が 192 行しかなく、日本語に限った規約が対象を自動的に絞る。

この数は着手時点のスナップショットであり、除外の一覧を確定させる前に測っている（いま測り直すと数はわずかに下がる）。**適用の直前には測り直すこと。** 「うち日本語」は行単位で数えた概算である（変換の対象判定は後述のとおり段落単位なので、実際の対象はこれより少し多い）。

## 規約

置き場所は**グローバル `CLAUDE.md` の § 言語**。`~/.claude/CLAUDE.md` は `dotfiles/.claude/CLAUDE.md` への symlink であり、全リポジトリに届く経路はこれだけである。`.claude/rules/` は symlink されておらず dotfiles 内でしか効かないので、全 repo に効かせる規約の置き場所にならない（`tasks/009` が作った `.claude/rules/skill-language.md` は自作スキルの md だけが対象なので、dotfiles 内で閉じていて問題ない）。

判断の余地がない規則なので、細則ファイルは作らず一文で置く。

> **日本語の本文とコメントは桁数で折り返さない**（語や句の途中で切らない）。エディタが soft-wrap するので二重に折れ、日本語は語の間に空白が無いため語の途中で切れる。**文の切れ目（`。`）での改行は折り返しではないので、そのままでよい**（意味のある位置で切れているため害が無い）。

## 変換の規則

段落の途中で改行されている行を次の行と結合する。

**文の切れ目での改行は折り返しではない。触らない。** 前の行が `。` `！` `？` で終わっているなら（末尾に `**` や `）` のような閉じ記号が付いていてもよい）、そこで結合を止める。

これは当初の規則から直したものである。はじめは「1段落＝1行」として段落の途中の改行をすべて結合していたが、それは規約を広く取りすぎていた。このタスクが問題にしているのは「日本語は語の間に空白が無いため**語や句の途中で割れる**」ことであり、害の根拠も「エディタが soft-wrap するので**意味と無関係な位置で**2回切れる」である。文末は意味のある位置なので、そこで切れていても害が無い。実際、dotfiles に当てたとき旧規則が結合した改行 118 件のうち 31 件（26%）は文末で終わっており、それらは桁数の折り返しではなく「1文1行」という書き方だった。

**`Run:` と `Expected:` の対は、空行を挟んで別の段落にした。** 実装計画はこの対を空行なしの隣接行で書いていたので、markdown では1つの段落であり、描画は元から1行に繋がっていたし、結合の対象にもなった。手順書として読むには2行に分かれていてほしいので、空行を入れて意図どおりの別段落にした（20 箇所を分け、元から2行だった 32 箇所にも空行を入れて揃えた）。折り返しの結合とは別の、markdown の書き方の修正である。**今後 `writing-plans` で計画を書くときは、この対のあいだに空行を置く。**

**触らないもの:**

- frontmatter（ファイル先頭の `---` ブロック）
- コードフェンス（`` ``` `` および `~~~`）の中 —— **フェンスを閉じられるのは、開いたときと同じ文字で、同じ長さ以上のマーカーの行だけである。**それより短いマーカーや別の文字のマーカー、情報文字列（言語名）が付いた行は中身であって、閉じない。閉じられないままファイルが終わる場合は最後まで中身として扱う。当初の実装はマーカーの文字と長さを見ず、マーカーに当たるどの行でも開閉を反転させていた。そのため 4 個のバッククォートで開いたフェンスの中に 3 個の行があると、そこから先のフェンスの内と外が入れ替わり、本来コードである `` ```ts `` ブロックが本文として結合された（TypeScript が 1 行に潰れた）。**この壊れ方は検証の3条件をすべてすり抜ける。** 文字は欠けず、構造の数も変わらず、段落の頭のインデントも変わらないからである。適用先の repo で 16 ファイルの変換結果が変わった。判定は `unwrap.py` と `measure_wraps.py` で同じにし、一致はテストで固定する

- 表の行（`|` で始まる）
- 見出し（`#`）、引用（`>`）、水平線
- 半角空白4つ以上またはタブで始まる行 —— markdown ではこれもコードブロックである
- **意図的なハードブレイク（行末が半角空白2つ、または `\`）を含む段落** —— 段落ごと触らない。ハードブレイクの前後だけ結合を止める形にすると規則が込み入るわりに、実数は joifup の notes 全体で15件しかない
- 日本語を含まない段落 —— 英語は空白で切れるので害が小さく、規約も日本語に限っている。**判定は行単位ではなく段落単位で行う。** 行単位にすると、英語の行で始まって日本語の行が続く段落が途中までしか結合されず、かえって読みにくい形で残る

**結合するもの:** 上記に当たらない段落本文の行と、箇条書き（`-` / `1.`）の項目本文が複数行に折られている場合の継続行。継続行は親の行に結合する。

**行頭のインデントは必ず戻す。** 箇条書きの項目の中には、空行を挟んでインデントされた段落が続くことがある。結合のために行を `strip()` したあとインデントを戻し忘れると、その段落が桁 0 に出てリストがそこで切れる。実装で実際に3件起きた。しかも**検証はこれを見つけられない** —— リスト項目の数は変わらず、段落テキストの比較は空白を無視するからである。だから検証に頼らず、結合の側でインデントを保つ。

**結合点の空白:** 結合点の**前後がともに日本語**（かな・漢字・全角の記号）なら空白なしで繋ぎ、**それ以外は半角空白1つ**を入れる。ただし全角の約物には例外を置く。**左が全角の句読点（`。` `、`）なら、右が何であっても空白を入れない。** **右が全角の開き括弧（`（` `「` `『` `【` `〔`）なら、左が何であっても空白を入れない。** 日本語では句読点の直後にも開き括弧の直前にも空白を置かないからである。

**閉じ括弧の側（`）` `」` `』` `】` `〕` が左）には例外を置かない。** 上と同じ数え方で `）` の直後に半角の可視文字が来る形を数えると、空白なしが 2,430 件・空白ありが 2,172 件（53:47）で、開き括弧の側の 93:7 のような支配的な慣習が無い。どちらに倒しても既存の書き方のおよそ半分に反することになるので、例外を置かず一般の規則（両側が日本語なら空白なし、それ以外は半角空白1つ）に委ねる。

どちらも既存の書き方から決めた。**数え方は次のとおりである。** 対象は折り返しが集中している 2 つの repo の *.md 926 ファイル（`unwrap.py` の除外一覧を当て、frontmatter とコードフェンスの中は数えない）。位置は行の内側（改行をまたがない位置）に限る。ここで「ascii」は**日本語でない文字**、すなわち `unwrap.py` の `JA`（かな・漢字・全角の約物）に当たらない文字を指す。ASCII の記号もバッククォートも含む。結合点の判定が「両側が日本語か」で書かれている以上、数えるべきもそれと同じ切り方である。この数え方で `（` の直前を見ると、空白なしが 12,470 件、空白ありが 920 件で 93% が空白なしである。ASCII 英数（`[A-Za-z0-9]`）に狭めると 4,314 件 対 2 件になる。どちらの切り方でも、開き括弧の直前に空白を置かないのが支配的である。例外を置かないと、`実体パスへ解決される。 ` ＋ `` `brew upgrade tmux` `` のような箇所と、`` `.claude` `` ＋ `（対象は…` のような箇所に空白が入る。dotfiles では前者が 18 箇所あった。後者は、例外を片側だけにしていた時点で、その 2 つの repo に当てると `（` に 531 件・`「` に 65 件の空白が新しく入る計算だった（同じ対象・同じ除外で、右側の例外を外したときに空白が入る結合点を数えた値。`「` は当初 55 件と書いていたが片方の repo の分しか数えていなかった）。

判定を「どちらかが ASCII 英数か」で書くと規則が変わってしまう。記号どうし（`:` と `` ` ``、`` ` `` と `—`）が結合点に来たときに空白が落ち、`使う:` と `` `brainstorming` `` が `使う:`brainstorming`` のようにくっつく。実装で実際に起きた。見るべきは「両側が日本語か」であって「片側が英数か」ではない。

折り返しで消えた空白は復元できないので、既存の本文の慣習に寄せて決めた。行の内側（改行をまたがない位置）で英数字と日本語の境界に空白が入っている割合を主な 3 つの repo の notes で数えると、日本語 → 英数字が 38,190 / 68,846（55%）、英数字 → 日本語が 60,260 / 85,315（71%）で、どちらも空白を入れる側が多数派である。`Claude Code` のように英数字の語句が行をまたいで割れた場合に語が潰れるのは、この規則でも防げる。

## 直り切らないものを見えるようにする

**4スペース以上のインデント行は触らない。** markdown では、その行がインデントされたコードブロックなのか、箇条書きの項目の継続行なのかを一般に区別できない。コードブロックを結合すると壊れるので、触らない側に倒す。結果として、継続行が4スペース以上で書かれた入れ子の箇条書きは折り返しが残る。

残ったものを黙って残さないために、**適用したあとに折り返しの残量を測って報告する。** 変換スクリプトが「変更なし」と答えることと、そのファイルに折り返しが残っていないことは別である。前者だけを見て終わりにすると、直り切らなかった分が「直った」ものとして扱われる。

次の2つは、実装の途中でレビューが「壊れる入力がある」として挙げたものである。どちらも実データを当たると `~/Joifup` 配下に1件も無かったが、扱いは分けた。

- **先頭が `|` でない GFM 表**（`列 | 値` のヘッダに `---|---` が続く形）は表と認識されず、結合されて壊れる。しかも壊れ方が検証の2条件のどちらにも引っかからず、安全と誤判定される。**検証がすり抜けること自体が問題なので、表の区切り行を構造として数えるようにした。** 結合で区切り行が消えると数が変わり、そのファイルは失敗として書き戻されない。
- **Setext 見出しの `===` 下線**は見出しの境界と認識されず、前の行と結合される。0 件なので対処しない（`---` 下線のほうは水平線として扱われるので結合されない）。将来書き始めたときのために、壊れることだけ記録しておく。

**引用（`>`）の中の折り返しも残る。** 引用行は触らないので、引用の中で文の途中や強調の途中に改行があってもそのままである。しかも残量の測定でも引用行は数えないので、**残ったことが数にも出ない。** dotfiles では2箇所だが、引用を多く使う repo ではもっと残る。

## 検証

21,940 行を目視せずに安全だと言える根拠を、スクリプト側に持たせる。ファイルごとに変換前後を比べ、次の3つがすべて成り立つときだけ書き戻す。

1. **段落テキストが文字単位で一致する。** 変換後から改行と結合時に挿入した空白を除いたものが、変換前から改行を除いたものと一致する。文字の欠落・重複・順序変更が無いことを保証する。
2. **構造の数が不変である。** 見出し・コードフェンス・リスト項目・表行・表の区切り行の数が前後で変わらない。
3. **段落の頭のインデントの並びが不変である。** 段落の先頭行（空行の次の非空行）の行頭インデント幅を順に並べたものが、前後で一致する。

どれかが崩れたファイルは変換せず、失敗として報告する。

3つ目は、**インデントを落としてリストを切る壊し方が1つ目も2つ目も素通りする**から要る。リスト項目の数は変わらず、段落テキストの比較は空白を無視するので、どちらも気づかない。実際に一度これで3箇所を壊した。結合の側でインデントを保つ実装にして直したが、検証にも同じことを見させておく。見るのは段落の先頭行だけなので、結合されずに複数行のまま残った段落の2行目以降のインデントは見ていない。

スクリプトには「触らないもの」の項目ごとに単体テストを付ける。フェンス内・表・ハードブレイク・frontmatter・英語段落がそれぞれ保存されること、日英境界に空白が入ること、リスト継続行が結合されることを固定する。

## 適用の範囲と順序

**この作業（tasks/008）で行うのは、規約の追加と dotfiles 自身の変換、そして変換スクリプトの確定まで。**

**スクリプトは `.claude/scripts/` にコミットする。** 当初は「一度きりの機械的変換だから恒久的な道具を持たない」として scratchpad に置く方針で始めたが、適用先が dotfiles だけでなく他の repo にも及ぶことが決まった時点で前提が崩れた。道具は複数回使われる。

スクリプトを残さない場合、リポジトリに残る唯一の正典は実装計画に埋め込まれたコードになる。**実際にそれが古いまま取り残された。** 実装の途中で規則が3回変わった（ハードブレイクの扱い、インデントの復元、結合点の空白）のに、計画のコードはその前の版のままだった。そのまま次の repo に当てれば、いま直した欠陥をそっくり再現する。とくに、実装中に入れた「除外は対象ディレクトリからの相対で判定する」という修正はどこにも記録されていなかった。これが無いと worktree の中で走らせた瞬間に全ファイルが除外され、**「変更なし・失敗 0」と出て成功に見える。**

**「変更なし・失敗 0」に見える形は他にもある。** 対象ディレクトリを渡し忘れると、何も走っていないのに同じ行が出て exit 0 していた。引数が空なら使い方を表示して exit 2 する。**打ち間違いも同じ形になる。** 存在しないディレクトリを渡したとき、走る対象が 0 件でも同じ行が出て exit 0 していた。対象がディレクトリとして存在しなければ、その旨を出して exit 2 する。`measure_wraps.py` も同じ扱いにする。除外には `node_modules` などに加えて `.superpowers` と、worktree の置き場所である `worktrees` `.worktrees` の両方を入れてある。repo ルートを渡したときに SDD の作業ファイルまで書き換えないためである。**除外はパスの接頭辞ではなく、対象ディレクトリからの相対パスの要素名で判定する。** 接頭辞で持つと、同じ除外が対象の渡し方によって効いたり効かなかったりする。`"/.claude/worktrees/"` を接頭辞で持ったまま対象を `<repo>/.claude` にすると、相対パスが `/worktrees/...` になって一致せず、**進行中の別ブランチの worktree を書き換える。** 実際、main の dotfiles で `unwrap.py .claude` を dry-run すると 95 件のうち 86 件が対象になり、うち 70 件が worktree の中のファイルだった。しかも実装計画が案内していたのがまさに `<WT>/.claude` の形である。要素名で判定すれば、対象をどこに置いても、また対象の内側でも外側でも同じように効く。除外の一覧は `unwrap.py` と `measure_wraps.py` で同じにし、**一致はテストで固定する**。片方だけが数えると、変換しないと決めた場所の折り返しが残量に出て、直し切れない数がいつまでも残る。読めないファイルが1件あっても全体を落とさず、そのファイルを失敗として報告して続ける。他の repo には壊れたファイルがありうる。

テストが付いているので、次に使う人はまずテストを走らせて、道具が壊れていないことを確かめられる。これが埋め込みコードには無い。

置き場所は `.claude/skills/<skill>/scripts/` ではなく `.claude/scripts/`。これはワークフローの入口ではなく、移行のための道具だからである。適用が全 repo で終われば消してよい。
